| N22 | **High** (packaging) | Published Helm charts 2.8.1-2.8.4 | The charts published at `opensearch-project.github.io/opensearch-k8s-operator` are not usable as a 2.x operator beyond 2.8.0: charts **2.8.1** and **2.8.2** default to image `opensearchproject/opensearch-operator:2.8.0` but render `--enable-webhooks=true --webhook-port=9443` plus a `ValidatingWebhookConfiguration`; the 2.8.0 binary exits with `flag provided but not defined: -enable-webhooks`, so a plain `helm install --version 2.8.2` crash-loops. Net effect: no published chart installs a working 2.x operator with default values today. | N23 | **High** (ops safety) | CRDs are templated without a keep policy | `templates/crds.yaml` renders every CRD from `files/*.yaml` when `installCRDs=true` and none carries `helm.sh/resource-policy: keep`. Consequences observed/derived: (a) `helm uninstall opensearch-operator` deleted all `opensearch.org` and `opensearch.opster.io` CRDs (verified: `kubectl get crd | grep opensearch` = 0 afterwards), which cascades into deleting every OpenSearchCluster object in the Kubernetes cluster; (b) upgrading with `legacyAPI.enabled=false` drops the `opensearch.opster.io` CRDs and therefore any not-yet-migrated legacy CRs. Helm's documented convention (`crds/` directory or the `keep` annotation) avoids both. Suggest adding `helm.sh/resource-policy: keep` to the rendered CRDs (at least the cluster CRDs) and documenting the legacyAPI switch as destructive. | `helm uninstall` during this run; chart source `charts/opensearch-operator/templates/crds.yaml` |
| N24 | Low | Securityconfig retry backoff | Follow-up to N17: the retry counter lives only in the `Securityconfig: Failed` component-status conditions (`retry:N`, `lastRetry:`), and the status is rewritten as `Running` with no conditions as soon as the retry job is active (`pkg/reconcilers/securityconfig.go:429-434`). `securityConfigRetryCount()` therefore reads 0 on the next failure: the backoff never grows beyond the 30 s initial delay and every Warning event reports `attempt 1`. | `88-issue-1456-securityconfig-job-retry` (event "attempt 1", status back to `Running` ~1 min later) |
| N25 | **High** (2.x -> 3.0 upgrade) | Legacy cluster migration blocked by the operator's own webhook | After upgrading a 2.8.0-managed cluster to the 3.x operator (legacyAPI enabled), the `clustermigration` controller never creates the `opensearch.org/v1` twin: its first write to the legacy CR (adding the migration finalizer, `controllers/migration_controller.go` ~line 140) is rejected by `vopensearchcluster.opensearch.opster.io` with "Direct updates to old API group OpenSearchCluster resources are not allowed", forever (error every backoff, no event on the CR). The cluster keeps running but is unmanaged by 3.x (main reconciler only watches `opensearch.org`). Root cause: `DashboardsConfig.Replicas int32 \`json:"replicas,omitempty"\`` with `+kubebuilder:default=1` (`api/v1/opensearch_types.go:229-230`, same in `api/opensearch.org/v1`): a stored `dashboards.replicas: 0` (dashboards disabled, as written by the 2.x operator/users) is omitted by the typed client, the CRD default turns it into `1` on the request, and `isStatusOnlyUpdate` (`webhook/legacy_webhook_helpers.go:25`, byte comparison of the specs) sees a spec change. Reproduced without the operator: `kubectl replace --dry-run=server` of the stored CR round-tripped through the `opsterv1` Go type is denied; the same object with `replicas: 0` restored is accepted; every other serialisation difference (`bootstrap.diskSize: "0"`, `8760h0m0s`, dropped empty `name: ""`, added `operatorClientCert: {}`) is tolerated. Fix: make `Replicas` a pointer or drop `omitempty` where a default exists (also stops the 3.x typed updates from silently flipping 0 -> 1), and let the legacy webhook allow requests from the operator's own service account or metadata-only changes. Note also that nothing surfaces the stuck migration to the user (no event/condition on the legacy CR), and deleting such an unmigrated legacy CR then hangs forever: the 2.x `Opster` finalizer is only removed by `handleOldClusterDeletion` for clusters that were migrated and deleted through the new CR (`migration_controller.go:383-398`), so the namespace stays `Terminating` until the finalizer is patched away by hand. | `50-operator-upgrade` on cb621e5 (chart 2.8.0 -> local): operator upgrade itself clean (pods untouched, green, data intact), then `set_api_group` finds no `opensearch.org` CR after 10+ min; operator log `clustermigration ... Reconciler error ... Direct updates ... not allowed` |
| N26 | Medium (document / verify) | Migration rolls every node | Once N25 is sidestepped (legacy CR stored with `dashboards.replicas: 1`), the migration itself works: the `opensearch.org` twin is created with status, certificate secrets are re-owned, and within seconds the 3.x reconciler logs `Deleting statefulset while orphaning pods`, `Creating bootstrap pod` (for an initialized 3-node cluster; the pod is deleted again a few seconds later), `Starting securityconfig update job`, then `Starting global candidate rolling restart`: all three nodes are replaced one at a time (2m apart), health stayed green, `RollingRestart: Finished` ~5 min after the operator upgrade. So an operator upgrade is not transparent for existing clusters: every 2.x cluster gets a full rolling restart, a securityadmin run and a transient bootstrap pod as soon as the new operator starts, with no opt-in or pacing across clusters (an operator with N clusters restarts them all concurrently). Worth documenting in the upgrade guide and, ideally, skipping the bootstrap pod for a migrated/initialized cluster (same code path as N21). Also seen: the migration controller hits an optimistic-lock conflict on its first pass (`the object has been modified`), harmless. | `51-operator-upgrade-migrated` on cb621e5: `upgrade_operator` saw all pods replaced; events `RollingRestart Starting/completed`; operator log 19:41:48-19:47 |
