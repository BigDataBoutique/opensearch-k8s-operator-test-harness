## Confirmed by runs

| # | Severity | Area | Finding | Evidence |
|---|---|---|---|---|
| N1 | **High** | Upgrade abort | Upgrading to an unpullable version (3.0.0 -> 3.99.0) deletes the first pod, which comes back in `ImagePullBackOff`. Reverting `spec.general.version` to 3.0.0 updates the StatefulSet template (`OnDelete` strategy) but the operator never deletes the stuck pod: `DeleteStuckPodWithOlderRevision` only handles `CrashLoopBackOff` (`pkg/helpers/helpers.go:925,952`), the cluster reconciler loops on "Waiting for statefulset to become ready", and the CR stays `UPGRADING` with `componentsStatus` still holding `__upgrade_target__: 3.99.0` (log says "Resetting upgrade progress for new target version" but the status is not rewritten). The cluster stays yellow at 2/3 nodes indefinitely; a typo in the version field needs manual pod deletion to recover. Suggested fix: treat `ImagePullBackOff` / `ErrImagePull` / `InvalidImageName` on an older-revision pod like CrashLoopBackOff, and clear Upgrader statuses when the target is reset. | `23-upgrade-abort` fails at the revert step; namespace kept for inspection (`logs/23-upgrade-abort-*/`) |
| N10 | **High** | Bootstrap / quorum (#1448) | A fresh cluster with a single cluster-manager-eligible node (pool `solo`, replicas 1, roles cluster_manager+data+ingest, OpenSearch 3.8.0) never forms. The bootstrap pod `os-<c>-bootstrap-0` (node id `Vab1MEFD…`) becomes cluster manager, the solo node joins, the operator deletes the bootstrap pod about a minute later without a voting-config exclusion, and the solo node then loops on `cluster-manager not discovered or elected yet, an election requires a node with id [Vab1MEFD…]` (`ClusterFormationFailureHelper`) forever; `_cluster/health` returns 503 `cluster_manager_not_discovered_exception`. Meanwhile the CR reports `phase: RUNNING`, `initialized: true`, so the operator believes the cluster is healthy. This is the bootstrap-removal case of upstream issue #1448 (no `_cluster/voting_config_exclusions` call anywhere in the operator). Three-manager clusters survive bootstrap removal because the remaining nodes still hold a majority. | `76-deletion-semantics` namespace_deletion phase (1-manager cluster); regression playbooks 81/82 target it directly; logs in `logs/76-deletion-semantics-*/` |
| N11 | **High** | emptyDir recovery | With `persistence.emptyDir` on all three nodes, force-deleting all pods at once (the node-crash / eviction case the feature exists for) leaves every pod recreated by the StatefulSet within seconds but with empty data directories: all three loop on `cluster-manager not discovered yet, this node has not previously joined a bootstrapped cluster`, startup probes fail, containers restart. The operator never recovers: `emptyDirDataLossSuspected` (`pkg/reconcilers/emptydir_recovery.go:24-28`) only fires when pod *objects* are missing ("not merely not-ready"), so with a StatefulSet recreating pods immediately the condition is never true, no `EmptyDirRecovery` status or event appears (12+ minutes observed, grace period is 5), and the CR keeps `phase: RUNNING`, `initialized: true`. Suggested fix: detect loss from the nodes themselves (all pods not ready past the grace period and node logs / `_cluster/state` showing no bootstrapped cluster, or cluster UUID changed) instead of pod existence. | `74-emptydir-total-loss` (expect_event timed out after 720 s); `logs/74-emptydir-total-loss-*/` |
| N7 | Medium | Webhook / TLS | `validateTlsConfig` (`webhook/opensearch_cluster_webhook.go:163`) only checks "transport TLS is enabled but neither generate nor secret is provided" when `security.tls.transport.enabled` is explicitly `true`, but the operator treats an unset `enabled` as enabled (`pkg/helpers/helpers.go:169-184`). A CR with `transport: {generate: false}` and no secret is therefore accepted by the webhook and the cluster can never come up. The same pattern exists for `http`, but there the later admin-secret rule ("admin secret name is not provided but http.tls generate is not true") still rejects the CR, so only transport is unguarded. Fix: use `helpers.IsTransportTlsEnabled` / `IsHttpTlsEnabled` in the webhook instead of the raw pointer. | `70-webhook-validation` (step marked `continue_on_error`, fails by design) |
| N12 | Low | Logging (disk resize) | `maybeUpdateVolumes` logs `r.logger.Info("Disk sizes differ for nodePool %s, Current: %s, Desired: %s", component, current, desired)` (`pkg/reconcilers/cluster.go:654`), printf-style on a structured logr logger. zap emits `dpanic` "odd number of arguments passed as key-value pairs for logging" (`ignored key: 6Gi`) on every diskSize change; in a development-mode logger this is a real panic. Use `Info("Disk sizes differ", "nodePool", component, "current", current, "desired", desired)`. | `75-disk-resize` (operator-status check flags the dpanic; the resize behaviour itself was as documented) |
| N13 | Low | Dashboards deployment | Every Dashboards Deployment is rolled twice at creation: ReplicaSet revision 1 (created 10:15:07) has the pod-template annotation `opensearch.org/last-applied: <compressed manifest>`, revision 2 (10:15:08) has no such annotation, and nothing else differs (`kubectl get rs -o json` diff of `spec.template`). The operator's 3-way-patch bookkeeping annotation is being written into the Deployment's pod template on the first create and stripped on the next reconcile, so the template hash changes and the pods are recreated. With `replicas: 2` that is four Dashboards pods for a minute on every cluster creation. Fix: keep the last-applied annotation on the Deployment's own metadata only, never inside `spec.template.metadata`. This resolves the earlier open item about two ReplicaSets. | `77-dashboards` (`validate_dashboards` counted 4 pods for 2 replicas) |
| N14 | Docs / UX | Custom TLS certificates | User-provided TLS secrets must hold PKCS#8 private keys: with cert-manager's default encoding (PKCS#1, `RSA PRIVATE KEY`) the securityconfig job dies with `java.io.IOException: algid parse error, not a sequence` (from `PKCS8Key.decode`) and every node crash-loops on the same error, while the CR reports RUNNING. `docs/userguide/main.md` (lines ~295, 660, 1593) only says "PEM-encoded" `tls.key`. Document `privateKey.encoding: PKCS8` for cert-manager users, and ideally have the operator (or webhook) detect a non-PKCS#8 key in the referenced secret and emit a clear event. | `65-tls-custom-certs` first run |
| N15 | Medium (#1448) | Manager scale-down | Scaling a dedicated cluster-manager pool 5 -> 3 (`smartScaler` on, data on separate nodes): the observer saw the member count go 7 -> 5 within one 5-second sample, i.e. both managers were removed back-to-back as soon as each reconcile found no shards on the node, with no voting-config exclusion; the cluster then rolled the remaining managers one at a time (5 <-> 4) for the config change. Health stayed green and the API was unreachable for at most 6 s, because OpenSearch's `cluster.auto_shrink_voting_configuration` still covers this case (it never shrinks below 3 voters). Below three managers (3 -> 1, or bootstrap removal on 1-2 managers, see N10) nothing protects quorum. | `80-issue-1448-manager-scale-down` |
| N16 | Low | Scaler stall warning | With a shard pinned to the node being removed (`index.routing.allocation.require._name`), the drain correctly never completes (fail closed, #1447) and the `DrainStalled` condition plus Warning event appear, but the Warning fired 22 minutes after `drainStarted` (10:12:28 -> 10:34:40) although its text says "has made no progress for 15m0s". The timer apparently starts at the first emptiness observation rather than at drain start. Minor, but the doc/event text should match the actual latency. | `86-issue-1447-drain-fail-closed` |
| N2 | Low | Status | `componentsStatus` accumulates duplicate entries per pool: `Upgrader` (`data`/`Upgraded` twice during `21`; `nodes`/`Upgrading` twice during `23`) and `Scaler` (two identical `data`/`Excluded` entries with `DrainStalled` during `86`). | CR status captured during `21`, `23`, `86` |

| N9 | Info (OpenSearch, not operator) | Crash recovery | After two of three pods are force-deleted at once (grace 0), the operator recreates them within seconds, but two peer recoveries (`.opendistro_security`, `.plugins-ml-config`, source nodes-0 -> target nodes-2) stayed in stage `init` at 0% for 21+ minutes, past OpenSearch's 15-minute `internal_action_timeout`, holding both recovery slots so every other replica stayed unassigned and the cluster yellow. No errors in any node log; IO pressure was low by then. Restarting the recovery *target* pod did not help (recoveries re-hung at `init`); restarting the *source* node (the cluster manager holding the primaries, whose java had been SIGKILLed in place earlier) cleared it: the cluster was green within a minute with all 5000 documents intact. Operator-side there is nothing to fix; a stuck-recovery detector that restarts the source node would be a useful resilience feature. | `40-chaos` double_crash phase (non-blocking) |
